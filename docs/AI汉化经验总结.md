# AI 汉化经验总结（以 Equilinox 为例）

> 适用范围：需要给游戏/软件做中文汉化，且主要靠 AI 辅助完成。以下经验按工作流顺序排列，重点标注"踩过的坑"。

## 一、侦察阶段：先搞清楚文本都藏在哪里

1. **解包/解压主程序**（jar/zip/exe 资源），列出全部文件，把资源文件（csv/json/xml/txt）和程序文件（class/dll/so）分开。
2. **文本来源分三类，分别处理**：
   - 资源文件（如 `languageSheet.csv`）—— 主力，翻译这里就覆盖大部分界面。
   - 代码硬编码字符串 —— 用字符串搜索工具枚举，区分"用户可见"和"调试输出"。
   - 运行时拼接字符串（如 "Save " + 数字、任务描述拼接）—— 通常要改代码。
3. **先看游戏有没有官方本地化框架**：Equilinox 有 `Language` 枚举 + CSV 加载器，但枚举里只有 English——最省事的是"替换英语列"而不是加新语言（加语言要改字节码和 UI）。
4. **检查字体系统，这是汉化成败的关键**：
   - TrueType/动态字体：直接替换字体文件即可，简单。
   - 位图字体（BMFont 的 .fnt + .png）：必须重新生成图集、补中文字形，是最大的工作量来源。

## 二、位图字体汉化：本项目最大的坑

### 必须复刻游戏解析器的坐标语义（血的教训）

游戏读取 .fnt 时，把 `x,y` 当作**带内边距的格子左上角**，墨迹实际在 `x+padding`。我一开始把 `x,y` 写成了"墨迹起点"，导致：

- 每个字形四边形的采样范围向右/下多伸了 10px
- 正好伸进**相邻字形**的墨迹 2px
- 症状：文字边缘出现与文字同色的杂点/细线，像"字被截断剩下的边缘"，有的在字内有的在字外

这个 bug 让 AI（和我）排查了很久，方向错了好几次（怀疑过 alpha、mipmap、^ 标记……）。**最终是靠对比一个"无此问题的旧补丁"才定位到坐标语义差异**。

**教训**：
- 生成字体前，先读游戏的字库解析代码，确认 `x/y/width/height/xoffset/yoffset/xadvance` 的确切含义。
- 找一个已知正常的样本（原版字体或社区补丁）逐项对照。
- 写像素级验证脚本：把字形按 .fnt 坐标从图集提取出来，与直接渲染的参考字形逐像素对比，确认墨迹位置和内边距正确。

### 其他字体要点

- **alpha 渐变 profile 要匹配**：原版字形是柔和渐变（内部 alpha 最高 ~172），着色器据此做平滑。生成的新字形若全是硬边 255，边缘就会偏硬/锯齿。
- **超采样**：以 2~16 倍尺寸渲染再缩小，能得到更平滑的抗锯齿，且不改变笔画粗细；这在构建期完成，**不影响游戏运行时性能**。
- **mipmap**：对"文字比图集字形小"的缩小显示很重要，别轻易关掉。
- **着色器平滑带**：smoothstep 带宽修改是全局的，会影响所有文字。原版英文字形 alpha 渐变和中文不同——加宽带宽会让英文"发虚像雾化"。改之前想清楚影响面。
- **字体风格匹配**：英文无衬线（如 Gill Sans）→ 中文字体可按风格选：圆体（圆润）、思源黑体/兰亭黑（现代人文）、楷体（手写治愈）、宋体（书卷）。中文字体没有真正的"condensed"，要紧凑感只能选字面偏窄的或用比例压缩。

## 三、文本翻译阶段

- **占位符必须保留**：`$0$`、`%s`、`{0}` 等原样保留，翻译时套进去。
- **标记字符要小心**：Equilinox 用 `^...^` 做高亮标记，但游戏代码**根本没有实现高亮处理**，`^` 会被当作普通字符渲染成字形（实心椭圆），看起来就是"字周围的同色小点"。翻译后要检查这类标记是否真的被游戏处理，没有就移除。
- **中文没有空格**：依赖空格断词的引擎会出问题（见下节），翻译时可以在句读处断句，但更稳妥的是修引擎。
- 维护一份**术语对照表**（生物群系、特性、进化……），全项目统一。

## 四、渲染/布局引擎：中文特有的问题

Equilinox 的 TextLoader 只按空格断词 → 长中文是一个"单词" → 放不进固定宽度盒子 → 顶点为空 → 除零崩溃。

**修复 = 字符级换行**，但引出第二个坑：换行拆出的多个"词"之间，引擎会按词距加空格 → 出现"点击 世界中"这种多余空格。

**解法**：给 Word 加 `spaceBefore` 标记——只有原文真的有空格的位置才留字距，中文连排不加。

**通用教训**：修改布局引擎时，要追踪"间距/换行/对齐"的每一个来源，别只盯着崩溃本身。

## 五、字节码/代码补丁

- **字符串常量替换**（class 常量池）适合改短文本，但要解析 class 格式（常量池条目、modified UTF-8）。
- **重编译**更可靠：用反编译器还原源码 → 修改 → `javac --release 8`（兼容旧 JRE）→ 替换 class。适合 MyFile（改编码）、TextLoader、TimeDisplay 这类简单类。
- 改编码时注意：Java 8 默认用系统编码读文本（中文系统是 GBK），要显式改成 UTF-8，否则乱码。
- 硬编码字符串分"全局可替换"和"仅某类可替换"（如 "m"、"to" 这种短词只能按类替换）。

## 六、验证：多管齐下，别靠猜

1. **无头布局测试**：写一个用游戏自己的字体解析器和换行算法跑全部文本的测试，验证无缺字、无崩溃、换行正确。
2. **像素级截图分析**：AI 看不了图时，用程序分析截图像素（文字带位置、碎片检测、颜色分类），用数据说话。
3. **管线模拟**：用 Python 复刻游戏的字体解析+采样+着色器公式，把文本渲染成图片检查——能隔离"字体数据问题"和"GPU 问题"。
4. **对照实验**：同时存在多个怀疑因素时，一次只改一个，或直接对比"原版"和"已知正常的补丁"，找到唯一差异（本项目最终靠这个定位坐标 bug）。
5. **版本标记**：在游戏里加个可见版本号（如左下角"汉化 v6"），确认对方跑的是最新版，避免"改好了但没装上"的乌龙。

## 七、发布补丁程序

- **备份 + 自动恢复**：安装前自动备份原文件，一键恢复。
- **自动找安装目录**：读注册表（Steam）+ 常见路径 + 手动输入兜底。
- **两个版本**：
  - 精简版：只带改动文件，用系统自带工具（PowerShell）合成——体积小，适合分享。
  - 完整版：整个替换文件——兼容老系统，最简单。
- 批处理脚本用 **GBK 编码 + CRLF**，否则中文系统外的控制台会乱码/解析失败。
- 杀毒软件可能误报"修改主程序"的行为，使用说明里提前提示。

## 八、给 AI 协作的提醒（这次的真实教训）

1. **一次只改一个变量**：这次把 alpha、mipmap、^ 标记、坐标等多个因素叠在一起排查，绕了很多弯路。每个修复先单独验证，再叠加。
2. **"看起来像"不是证据**：症状像"截断的边缘"，实际是相邻字形串色。要用像素数据定位，而不是凭直觉猜原因。
3. **保留每个版本的产物**：能回退、能对照（本项目靠对比旧补丁定位了 bug）。
4. **验证要覆盖"对方的机器"**：分辨率、系统区域设置（GBK/UTF-8）、显卡都可能影响结果；把版本标记和日志留出来。
5. **占位符/标记/格式**：翻译交付前，用脚本检查：有没有漏译、占位符是否保留、有没有引入非法字符。

---

**一句话总结**：汉化的难点不是翻译本身，而是"文本→字体→渲染→验证"这条链路里，任何一个环节的格式语义不一致都会产生怪异的视觉 bug——所以先读懂解析器，再动手，然后像素级验证，最后对照已知样本收尾。
